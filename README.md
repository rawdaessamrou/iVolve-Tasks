# Cloud DevOps Accelerator Program — Hands On

## About This Repository

This repository brings together the full set of hands-on labs completed as part of the iVolve Cloud DevOps Accelerator Program, a track designed to build practical, end-to-end DevOps competency across the modern delivery pipeline. The program moved progressively from application build tooling through containerization, orchestration, continuous integration and delivery, GitOps, and finally infrastructure automation, mirroring the way a real production pipeline is assembled piece by piece. Rather than duplicating the detailed walkthroughs already written for each lab, this document exists to give a single, readable overview of the journey as a whole: what each stage covered, why it mattered in the context of the stage before it, and how the pieces connect into one coherent workflow.

The labs were completed individually and each carries its own README with the exact playbooks, manifests, Dockerfiles, and pipeline definitions used, along with verification screenshots. This overview is meant to sit above those individual documents, giving context to anyone browsing the repository for the first time, including recruiters and hiring managers evaluating the breadth of the work.

## Build Tools: Gradle and Maven

The program opened with the foundation of any CI/CD pipeline, the build step itself. Lab 1 covered building and packaging a Java application with Gradle, cloning source code, running unit tests, producing a runnable JAR artifact, and verifying the application executed correctly. Lab 2 repeated the same exercise using Maven, reinforcing the parallel concepts between the two most widely used JVM build tools and making clear why later Docker and Jenkins stages needed to accommodate either toolchain. Understanding both was important because real organizations often maintain legacy Maven projects alongside newer Gradle-based ones, and a DevOps engineer needs to be comfortable automating around either.

## Containerization with Docker

With working build artifacts in hand, the next seven labs focused on turning applications into portable, production-ready containers. Lab 3 introduced writing a Dockerfile from a Maven base image, building the application inside the container itself, and exposing the correct port. Lab 4 built on this by packaging the same Spring Boot application from a pre-built JAR on a lightweight Java base image, deliberately comparing the resulting image size against Lab 3 to demonstrate the cost of shipping build tooling inside a runtime image. Lab 5 resolved that tension directly through a multi-stage build, compiling in one stage and running from a minimal image in the next, which became the pattern carried forward into the CI/CD pipelines later in the program.

Labs 6 through 9 shifted focus from image construction to how containers behave at runtime. Lab 6 explored the three ways Docker allows environment variables to be supplied, at the command line, through an environment file, and baked into the Dockerfile itself, and applied all three against a single Flask application. Lab 7 introduced persistent storage concepts through both named volumes and bind mounts, using an Nginx container to show the practical difference between data that lives with Docker and data that lives on the host filesystem. Lab 8 moved into container networking, creating a custom bridge network to prove that containers on the same network can resolve and reach each other while containers left on the default network cannot, a distinction that matters directly for microservice communication. Lab 9 tied all of these concepts together in a Docker Compose stack pairing a Node.js application with a MySQL database, complete with health and readiness checks and a final push of the built image to Docker Hub.

## Kubernetes for Container Orchestration

The Kubernetes stage, spanning Labs 10 through 20, was the largest single block of the program and moved from cluster-level primitives toward a fully secured, production-shaped application deployment. It began with node isolation using taints, followed by namespace creation and resource quota enforcement to control how many pods a team could run in a shared cluster. Labs 12 through 14 built the data layer for the eventual application: ConfigMaps and Secrets to separate non-sensitive configuration from credentials, a Persistent Volume and Persistent Volume Claim backed by hostPath storage, and a StatefulSet running MySQL with a headless service in front of it, tying in the earlier taint by adding a matching toleration so the database pod could actually schedule onto the tainted node.

Labs 15 and 16 introduced the application itself, a Node.js deployment pulling its custom image from Docker Hub, consuming the same ConfigMap and Secret values as the database layer, tolerating the same taint, and mounting the previously defined persistent volume. An init container was then added ahead of the main application container specifically to create the application database and grant the correct privileges before the app ever started, a pattern commonly used to guarantee dependencies are ready before a workload begins serving traffic. Labs 17 and 18 hardened the deployment further, adding CPU and memory requests and limits to keep the workload from starving its neighbours, and a NetworkPolicy restricting MySQL ingress to only the application pods on port 3306. The Kubernetes stage closed with Lab 19 deploying a Prometheus node-exporter as a DaemonSet tolerant of all existing taints so that monitoring coverage reached every node regardless of scheduling restrictions, and Lab 20 introducing RBAC through a dedicated service account, a read-only Role scoped to pods, and a RoleBinding, the same access-control pattern later reused to grant Jenkins its own least-privilege identity inside the cluster.

## CI/CD Pipelines with Jenkins

Labs 21 through 23 assembled the continuous integration and delivery layer around everything built so far. Lab 21 established role-based authorization within Jenkins itself, separating an administrative user from a read-only one. Lab 22 built the first full pipeline, chaining unit testing, application build, Docker image build, a push to Docker Hub, local image cleanup, an update to the Kubernetes deployment manifest with the new image tag, and a final deployment to the cluster, with post-build actions defined for success, failure, and completion regardless of outcome. Lab 23 extended this into a more mature engineering pattern, introducing a Jenkins shared library so that steps like building, scanning, and deploying images could be written once and reused cleanly across multiple pipelines, and configuring a Jenkins agent so the pipeline executed on dedicated build infrastructure rather than the controller itself.

## GitOps Workflow with ArgoCD

Lab 24 completed the delivery story by layering a GitOps workflow on top of the existing pipeline using ArgoCD. Rather than Jenkins deploying directly to the cluster, the pipeline was adjusted to build and push the image, update the Kubernetes manifests with the new image reference, and push those manifest changes back into a Git repository, with ArgoCD watching that repository and reconciling the live cluster state to match it automatically. This shift, from a pipeline that pushes changes to a controller that pulls them, is the core idea behind GitOps and gave the whole delivery chain a single auditable source of truth in Git.

## Linux Automation with Ansible (RH294)

The final five labs, drawn from the RH294 curriculum, moved the focus from application delivery to infrastructure configuration itself. Lab 25 covered the fundamentals of getting Ansible working at all: generating and distributing SSH keys to a managed node, building an inventory, and running a first ad-hoc command to check disk space. Lab 26 introduced playbooks proper, automating the installation and configuration of an Nginx web server and a custom web page. Lab 27 restructured that same kind of work into reusable Ansible roles, one each for Docker, kubectl, and Jenkins, reflecting the same tools introduced earlier in the program but now provisioned in a repeatable, idempotent way rather than by hand.

Lab 28 introduced Ansible Vault, encrypting the database password used by a playbook that installed MySQL, created the application database, and granted a dedicated user full privileges on it, keeping sensitive credentials out of plain text in version control. Lab 29 closed the program by connecting Ansible to live cloud infrastructure, using AWS EC2 dynamic inventory to automatically discover instances tagged for the database role and running the MySQL role against whatever hosts matched, rather than relying on a static, manually maintained inventory file.

## Closing Notes

Taken together, these 29 labs move through the same lifecycle a shipped application actually goes through: building code, packaging it into containers, orchestrating those containers reliably at scale, automating the pipeline that gets code from commit to cluster, adopting Git as the single source of truth for what should be running, and finally provisioning and configuring the underlying infrastructure so that none of the above has to be done by hand. Detailed configuration, exact commands, and verification screenshots for each individual lab are available in that lab's own README within this repository.
